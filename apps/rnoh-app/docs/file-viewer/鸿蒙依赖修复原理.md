# 鸿蒙两库修复原理 — 差什么、怎么修

> 适用：`@react-native-ohos/react-native-document-picker@9.3.2`、`@react-native-ohos/react-native-file-viewer@2.2.0`  
> 操作步骤见 [鸿蒙集成与修复说明.md](./鸿蒙集成与修复说明.md)；接入清单见 [鸿蒙接入指南-step-by-step.md](./鸿蒙接入指南-step-by-step.md)。

这两个库在鸿蒙上**不是装完就能用**。社区 npm 包的原生实现缺了几块关键逻辑，工程接入方式也不对。MARS 用 **patch 改 ETS → 写回 `.har` → JS 层补策略** 三步把它们串起来。

---

## 1. 整体链路

```
npm install
  └─ patch-package          # 改 node_modules 内 ETS 源码
  └─ repack-ohos-hars.sh    # 把 patch 写回 .har

harmony/entry/oh-package.json5   # 依赖 *.har（非源码目录）
harmony/entry → ohpm install → DevEco Rebuild → Run

JS: openPickedFilePreview.ts    # Harmony 预览策略
Demo: FileViewerDemo             # 手动验证（我的 → 功能演示 → 文件预览）
```

DevEco **实际编译的是 `.har`**，不是 `node_modules` 里解压出来的源码目录。只改 TS 不够，还要 [`scripts/repack-ohos-hars.sh`](../../scripts/repack-ohos-hars.sh) 把 patch 后的 ETS 塞回 `document_picker.har` / `file_viewer.har`。

### 1.1 两个常见踩坑

| 尝试                              | 结果                                                            |
| --------------------------------- | --------------------------------------------------------------- |
| `oh-package.json5` **链源码目录** | 启动崩溃：`cannot find record '&@react-native-ohos/.../ts&...'` |
| `hvigor assembleHar` 重打 `.har`  | 产出**字节码 har**，缺 `ts.ts`，编译或运行均异常                |

**结论：** 必须用 npm 自带的**源码格式 `.har`**，再把 patch 后的 ETS 写回 har。

## 2. DocumentPicker — 差什么、改了什么

Patch：[`patches/@react-native-ohos+react-native-document-picker+9.3.2.patch`](../../patches/@react-native-ohos+react-native-document-picker+9.3.2.patch)

| 原版问题              | 表现                                                                       | 修复                                                                     |
| --------------------- | -------------------------------------------------------------------------- | ------------------------------------------------------------------------ |
| 返回 `uri: fUri.path` | 把 `file://docs/storage/...` 剥成 `/storage/...`，**丢掉 picker 临时授权** | 改回 `uri: uri`，保留系统给的完整 URI                                    |
| `copyTo` 用原文件名   | 中文/特殊字符文件名 → PreviewKit **静默失败**                              | 新增 `getSafeCopyFileName()`，沙箱副本统一叫 `picked.pdf`、`picked.docx` |

**职责：** DocumentPicker 负责「选对文件 + 拷进沙箱」。它修不好，后面 FileViewer 拿到的路径/权限就是错的。

### 2.1 关键代码

**① 保留 picker 原始 URI**

```typescript
// 修复前
uri: fUri.path,

// 修复后
uri: uri,
```

`uri` 为系统返回的 `file://docs/storage/...`，带临时访问授权；`fUri.path` 仅为绝对路径，无法用于跨应用预览。

**② 沙箱副本使用 ASCII 文件名**

```typescript
private getSafeCopyFileName(sourceUri: fileuri.FileUri): string {
  const name = sourceUri.name ?? String(new Date().getTime());
  const dotIndex = name.lastIndexOf('.');
  const ext = dotIndex >= 0 ? name.substring(dotIndex) : '';
  return `picked${ext || ''}`;
}
```

磁盘上是 `picked.pdf`，JS 侧 `picked.name` 仍是用户所选原文件名；预览标题默认用 `picked.name`（见 `openPickedFilePreview.ts`）。

## 3. FileViewer — 差什么、改了什么

Patch：[`patches/@react-native-ohos+react-native-file-viewer+2.2.0.patch`](../../patches/@react-native-ohos+react-native-file-viewer+2.2.0.patch)

原版逻辑偏简单：**路径解析粗糙、PreviewKit 和 startAbility 选路不对、失败处理有 bug**。

| 原版问题                                         | 表现                                                                | 修复                                                          |
| ------------------------------------------------ | ------------------------------------------------------------------- | ------------------------------------------------------------- |
| 直接用传入 path，URI 不统一                      | `/storage/...` 和 `file://docs/...` 混用                            | `resolveFileTarget` / `resolvePreviewUri` 统一解析            |
| 外部存储 URI 错误                                | PreviewKit 认不出                                                   | `/storage/...` → `file://docs/storage/...`                    |
| 不区分沙箱 vs 外部文件                           | 路由混乱                                                            | `isAppSandboxPath()`                                          |
| PreviewKit 失败就 fallback startAbility          | 沙箱 PDF 失败时 JS 侧可能**仍 resolve**，用户看到「成功了但没预览」 | 沙箱路径 PreviewKit 失败 → **直接 reject**，不再错误 fallback |
| `startAbilityForResult` + 硬编码 `file://` + uri | unknown file / preview failed                                       | 改用规范 `previewUri`、`ohos.want.action.viewData`、权限 flag |
| mime 识别不全                                    | 部分扩展名 preview 失败                                             | `fallbackMimeType` 映射表                                     |
| `open()` 里 stat / PreviewKit 失败               | Promise 行为不一致                                                  | 统一走 eventEmitter + reject                                  |

**一句话：** FileViewer patch 补的是「鸿蒙上怎么正确打开一个文件」的路由和错误处理。

### 3.1 路由决策（patch 后）

```
open(filepath)
  └─ resolveFileTarget(filepath)     # path、previewUri、mimeType
  └─ fs.stat(path)
  └─ OpenFile(target, options)
       ├─ preferSystemOpen?          # showOpenWithDialog 或沙箱 txt
       │    └─ startAbilityOpen(...)
       └─ canPreview && !preferSystemOpen
            └─ OpenByFilePreview(...)
                 ├─ 非沙箱 URI → persistPermission 后再 PreviewKit
                 └─ PreviewKit 失败
                      ├─ 沙箱路径 → emit 错误，reject
                      └─ 外部路径 → fallback startAbilityOpen
```

## 4. JS 层还要再补一刀

原生修完后，业务侧仍不能照搬官方「直接 `FileViewer.open(uri)`」示例。Harmony 有两种路径，由 [`src/utils/openPickedFilePreview.ts`](../../src/utils/openPickedFilePreview.ts) 统一处理：

| 情况                                  | 打开什么          | 怎么开                                | strategy                  |
| ------------------------------------- | ----------------- | ------------------------------------- | ------------------------- |
| 有 `fileCopyUri`（沙箱 `picked.pdf`） | 沙箱副本          | PreviewKit，去掉 `showOpenWithDialog` | `harmony-sandbox-preview` |
| 没有副本                              | picker 原始 `uri` | 强制 `showOpenWithDialog: true`       | `harmony-picker-uri`      |
| 用户指定 `showAppsSuggestions`        | picker `uri`      | 原样                                  | `harmony-picker-uri`      |

DocumentPicker 调用固定带 `copyTo: 'documentDirectory'`，尽量走沙箱 PreviewKit 这条稳定路径。

```typescript
import {openPickedFilePreview, isCancel} from '@/utils/openPickedFilePreview';

try {
  const result = await openPickedFilePreview();
  console.log(result.statusLines);
} catch (e) {
  if (!isCancel(e)) throw e;
}
```

## 5. 同事 pull 之后要做什么

`package.json` 的 `postinstall` 已串联：

```bash
patch-package && bash scripts/repack-ohos-hars.sh
```

流程：

1. `npm install`（自动 patch + repack har）
2. `cd harmony/entry && ohpm install`
3. DevEco **Clean → Rebuild**
4. 验证：**我的 → 功能演示 → 文件预览**；页面底部可测「下载示例 PDF 并预览」

改 patch 后若 Rebuild 无效：

```bash
bash scripts/repack-ohos-hars.sh
cd harmony/entry && ohpm install
# DevEco Clean + Rebuild
```

## 6. 总结对照

| 库                  | 缺的核心能力                                 | 怎么修                           |
| ------------------- | -------------------------------------------- | -------------------------------- |
| **document-picker** | 正确的 picker URI + 稳定的沙箱文件名         | 小 patch（2 处）                 |
| **file-viewer**     | URI 解析、沙箱/外部路由、PreviewKit 失败处理 | 较大 patch（重写 OpenFile 流程） |
| **工程**            | patch 要进 `.har` 才能被 DevEco 编译         | `repack-ohos-hars.sh`            |
| **JS**              | 根据 `fileCopyUri` 选预览策略                | `openPickedFilePreview.ts`       |

Android 上这两个库基本 autolink 即可；**鸿蒙特有的 URI 授权、PreviewKit、沙箱路径**才是需要 patch 的原因。
