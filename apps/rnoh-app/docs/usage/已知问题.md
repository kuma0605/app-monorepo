## #001 · Metro 缓存导致新建文件无法解析

**日期：** 2026-04-23

**错误信息：**

```
ERROR  Error: Unable to resolve module @/components/PlatformButton
from .../src/screens/Home/index.tsx:
@/components/PlatformButton could not be found within the project
or in these directories:
  node_modules
```

**现象：**  
新建组件文件（如 `src/components/PlatformButton/`）后，import 语句报"找不到模块"，
但文件确实存在于正确路径，`@` 路径别名配置也正确。

**根本原因：**  
Metro Bundler 存在文件监听缓存，新增文件时缓存未及时更新，
导致 Metro 仍按旧的文件树解析模块，找不到新建的文件。

**解决方案：**  
携带 `--reset-cache` 参数重启 Metro，强制清除缓存：

```
npx react-native start --reset-cache
```

**规律：**  
以下操作后遇到模块找不到的报错，优先尝试清除缓存：

- 新增组件 / 工具文件
- 新增平台后缀文件（`.android.tsx` / `.harmony.tsx` 等）
- 修改 `babel.config.js` 或 `metro.config.js`
- 安装 / 删除 npm 包后未重启 Metro

## #002 · HarmonyOS 模拟器需要配置 abiFilters

**日期：** 2026-05-06

**现象：**
Windows 上使用 HarmonyOS 模拟器运行项目时报错，无法正常启动。

**根本原因：**
`build-profile.json5` 中未配置 `abiFilters`，默认只编译 `arm64-v8a` 架构的 native so 库，
而 Windows 模拟器是 `x86_64` 架构，缺少对应的 so 文件导致运行失败。

**解决方案：**
在 `entry/build-profile.json5` 的 `externalNativeOptions` 中添加 `abiFilters`：

```json5
"externalNativeOptions": {
  "abiFilters": ["x86_64", "arm64-v8a"],
  "path": "./src/main/cpp/CMakeLists.txt"
}
```

- `x86_64` — PC 模拟器（Windows / Mac Intel）
- `arm64-v8a` — 真机 + Mac Apple Silicon 模拟器

**官方文档：**
https://developer.huawei.com/consumer/cn/doc/harmonyos-guides/ohos-abi#arm64-v8a

## #003 · Harmony DocumentPicker + FileViewer 预览 unknown file

**日期：** 2026-05-19

**现象：**
从文件管理器选取 PDF 后，能进入 File Preview 页面，但提示 `unknown file: preview failed`；
或 JS 已调用 `FileViewer.open` 但无预览界面。

**根本原因：**

1. `@react-native-ohos/react-native-document-picker` 把 picker 返回的 `file://docs/storage/...` 转成了 `fUri.path`（`/storage/...`），**丢失 URI 临时授权**。
2. `@react-native-ohos/react-native-file-viewer` 对 `/storage/` 路径强制走 `startAbility`，且 PreviewKit 失败后会 fallback 到错误的 startAbility，导致 unknown file。
3. 原生 patch 必须通过 **`.har` 依赖** 引入（`harmony/entry/oh-package.json5` 指向 `document_picker.har` / `file_viewer.har`）。**不要链源码目录**，否则启动崩溃：
   ```
   ReferenceError: cannot find record '&@react-native-ohos/react-native-document-picker/ts&9.3.2'
   ```

**解决方案：**

1. 安装依赖并打 patch（`npm install` 会自动执行 `patch-package` 与 `scripts/repack-ohos-hars.sh`）：
   ```bash
   npm install
   ```
2. 同步鸿蒙依赖并重编 entry：
   ```bash
   cd harmony/entry && ohpm install
   ```
3. DevEco 打开 `harmony/` → **Sync** → **Build → Clean Project** → **Rebuild Project** → Run `entry`。
4. 更新 JS Bundle：`npm run dev`

**说明：** patch 改的是 `node_modules` 内 ETS 源码；`repack-ohos-hars.sh` 会把 patch 后的 ETS 写回 npm 格式的 `.har`。详细说明见 [docs/file-viewer/鸿蒙集成与修复说明.md](../file-viewer/鸿蒙集成与修复说明.md)。

**手动重打 har（改 patch 后）：**

```bash
bash scripts/repack-ohos-hars.sh
cd harmony/entry && ohpm install
```

**业务层用法：**
使用 [`src/utils/openPickedFilePreview.ts`](../../src/utils/openPickedFilePreview.ts)：

- 有 `fileCopyUri` → 打开沙箱 `picked.pdf`（PreviewKit）
- 无副本 → 打开 picker 原始 `uri` + `showOpenWithDialog`

## #004 · FormData 上传手动设置 Content-Type 导致失败

**日期：** 2026-05-21

**现象：**
调用 `uploadFile(formData)` 或 `dictateFeedBack(formData)` 上传文件时，请求失败或后台收不到文件；表现为 400、空文件、Network Error 等。注释掉 service 里的 `headers: {'Content-Type': 'multipart/form-data'}` 后可以正常上传。

**错误写法（勿用）：**

```ts
return apiClient.post('/file/upload', formData, {
  headers: {'Content-Type': 'multipart/form-data'}, // 缺少 boundary
});
```

**根本原因：**

1. `multipart/form-data` 必须带 `boundary`（如 `multipart/form-data; boundary=----WebKitFormBoundary...`），boundary 须与请求体分隔符一致，只能由发请求的原生层自动生成。
2. 手动只写 `multipart/form-data` 不带 boundary 时，RN 原生网络层无法正确封装文件体，后台无法解析。
3. `apiClient` 实例默认 `Content-Type: application/json`，FormData 上传若不做处理，也可能被错误 Content-Type 干扰。

**解决方案：**

1. **不要**在 upload service 里手动设置 `Content-Type: multipart/form-data`。
2. `apiClient` 请求拦截器对 `FormData` 须用 **`AxiosHeaders.setContentType(false)`** 清除默认的 `application/json`（axios 1.x 下 plain `delete headers['Content-Type']` 可能清不干净，见 **#007**）。由 RN 原生层生成带 boundary 的正确请求头（见 [`src/services/apiClient.ts`](../../src/services/apiClient.ts)）。
3. upload service 只需传入 `formData`：

```ts
export function uploadFile(formData: FormData) {
  return apiClient.post<UploadResult>('/file/upload', formData);
}
```

**规律：**
JSON 请求用 `application/json`；FormData 上传不传 Content-Type，由拦截器 + 原生层自动处理。

**相关文档：**
[文件上传指南](./文件上传指南.md) — 「Content-Type（multipart）」

## #005 · 鸿蒙相册图片 copyTo 失败导致上传 Network Error

**日期：** 2026-05-21

**现象：**
PDF 上传正常；从相册选 PNG/JPG 时上传 `Network Error`（`status: undefined`）。picker 返回类似：

```json
{
  "fileCopyUri": null,
  "copyError": "13900002 No such file or directory",
  "uri": "file://media/Photo/1/IMG_...",
  "type": "image/png"
}
```

**根本原因：**

1. `copyTo: 'documentDirectory'` 对相册图片在鸿蒙上可能失败（中文名、相册 `file://media/...` URI 等），`fileCopyUri` 为空。
2. 原生 `copyFile` 曾用 `'r+'` 打开只读相册文件，触发 `13900002 No such file or directory`。
3. RNFS 的 `normalizeFilePath` 会把 `file://media/...` 错误截成 `media/...`，JS 兜底复制也会失败。
4. 预览可走 picker 原始 `uri` +「打开方式」；**上传**需沙箱可读路径。

**解决方案：**

1. patch `@react-native-ohos/react-native-document-picker`：`copyFile` 改用 `'r'`，并优先用 picker 原始 `uri` 复制。
2. patch `@react-native-ohos/react-native-fs`：鸿蒙 `file://media/` URI 不参与 `file://` stripping。
3. 上传前调用 [`ensureUploadablePath`](../../src/utils/ensureUploadablePath.ts)（内部 RNFS copy / read+write 兜底）。

修改 patch 后需执行：

```bash
npm install
bash scripts/repack-ohos-hars.sh
cd harmony/entry && ohpm install
npm run dev
```

DevEco：**Clean → Rebuild → Run**。

> patch 文件须完整可解析，否则 `npm install` 会在 postinstall 失败，见 **#006**。

**相关文档：**
[文件上传指南](./文件上传指南.md)

## #006 · patch 文件不完整导致 npm install 失败

**日期：** 2026-05-21

**错误信息：**

```
**ERROR** Failed to apply patch for package @react-native-ohos/react-native-document-picker

This happened because the patch file patches/@react-native-ohos+react-native-document-picker+9.3.2.patch could not be parsed.

npm error command sh -c patch-package && bash scripts/repack-ohos-hars.sh && git config core.hooksPath .githooks
```

**现象：**  
执行 `npm install` 时 postinstall 在 `patch-package` 阶段失败，依赖装不完整；若强行跳过，鸿蒙相册图片上传相关原生修复也不会生效。

**根本原因：**

1. `patches/@react-native-ohos+react-native-document-picker+9.3.2.patch` 曾被**手工编写且截断**：最后一处 hunk 在 `copyFileStream` 中间（如 `let readSize = 0;`）就结束，缺少后续上下文行与函数闭合括号。
2. unified diff 的 hunk 必须包含完整变更块；截断后 `patch-package` 无法解析，整个 postinstall 链中断。
3. 用默认上下文的 `diff -u` 生成 patch 时，若变更块较长，也可能只输出不完整 hunk，同样无法应用。

**解决方案：**

1. 使用**完整上下文**重新生成 patch（示例）：

   ```bash
   # 对比 vanilla 与 patch 后的 documentPickerTurboModule.ts
   diff -U 999 vanilla.ts patched.ts > /tmp/dp.diff
   # 再按 patch-package 格式补上 diff --git / index / --- / +++ 头
   ```

2. 更推荐的标准流程——改 `node_modules` 后由工具生成，勿手写：

   ```bash
   npx patch-package @react-native-ohos/react-native-document-picker
   ```

3. 验证 patch 可解析且能打上：

   ```bash
   npx patch-package
   npm run postinstall
   ```

**规律：**

- 修改 `patches/*.patch` 后，本地务必跑一遍 `npx patch-package` 或 `npm install`，确认无 parse / apply 错误。
- 鸿蒙原生 patch 改完还需 `repack-ohos-hars.sh` + DevEco Rebuild（见 #003、#005）。
- 相关 patch 文件：
  - `patches/@react-native-ohos+react-native-document-picker+9.3.2.patch`
  - `patches/@react-native-ohos+react-native-fs+2.22.0-beta.3.patch`（相册上传 RNFS 兜底，同上需保证 patch 完整）

**相关文档：**
[鸿蒙集成与修复说明.md](../file-viewer/鸿蒙集成与修复说明.md) — patch 与 har 重打包

## #007 · Android 上传 Network Error（登录正常、鸿蒙可传）

**日期：** 2026-05-21

**现象：**

- Android：`fileCopyUri` 正常（如 `file:///data/user/0/.../xxx.jpeg`），但上传报 **「网络连接失败，请检查网络设置」**（`NetworkError`，无 HTTP 状态码）。
- 同一套代码、同一 `API_BASE_URL`：**登录等 JSON 接口正常**；**鸿蒙上传也可成功**。
- 容易误判为「手机连不上后台」或「文件路径不对」。

**示例 picker 结果（路径无问题）：**

```json
{
  "fileCopyUri": "file:///data/user/0/com.samrapp/files/.../xxx.jpeg",
  "uri": "content://com.android.providers.media.documents/document/image%3A1000000018",
  "name": "xxx.jpeg",
  "type": "image/jpeg",
  "size": 99811
}
```

**根本原因：**

1. 登录走 **JSON**（`Content-Type: application/json`），上传走 **FormData**（须 multipart + boundary），不是同一套请求逻辑。
2. `apiClient` 创建 axios 实例时默认 `Content-Type: application/json`。
3. axios 1.x 在 `transformRequest` 中：若仍检测到 JSON Content-Type，会把 **FormData 转成 JSON 字符串** 再发出，文件二进制丢失。
4. 旧拦截器用 `delete headers['Content-Type']` 在 **AxiosHeaders** 合并后可能**清不干净**。
5. **鸿蒙**原生网络层有时仍能按 multipart 发出；**Android（OkHttp）**更严格，常直接 `Network Error`。

**解决方案：**

在 [`src/services/apiClient.ts`](../../src/services/apiClient.ts) 请求拦截器中，对 FormData 使用：

```ts
import axios, {AxiosHeaders} from 'axios';

const headers = AxiosHeaders.from(config.headers);
if (config.data instanceof FormData) {
  headers.setContentType(false); // 勿用手动 multipart/form-data，也勿 plain delete
}
config.headers = headers;
```

**排查区分：**

| 情况                              | 说明                                      |
| --------------------------------- | ----------------------------------------- |
| 登录 OK、上传 Network Error       | 优先查本 issue（FormData / Content-Type） |
| `fileCopyUri: null` + `copyError` | 查 **#005**（鸿蒙相册 copyTo）            |
| 有 HTTP 状态码（400/413/500）     | 已到后台，查接口字段名、网关、MinIO 等    |

**规律：**

- Android 上传失败且 picker 已有 `fileCopyUri` 时，**先不要改** `ensureUploadablePath` 或网络配置。
- 与 **#004** 同属 FormData Content-Type 问题；#004 讲「勿手动设 multipart」；本 issue 讲 axios 1.x 在 Android 上的具体表现与 `setContentType(false)` 修复。

**相关文档：**
[文件上传指南](./文件上传指南.md) — 「Content-Type（multipart）」

## #008 · 上传报 header name must be a non-empty string（Harmony / RN）

**日期：** 2026-05-21

**现象：**

- 选文件、`fileCopyUri` 正常，上传时报：
  ```
  Error: header name must be a non-empty string
  ```
- 堆栈在 `axios/.../AxiosHeaders.js` → `xhr.js` 的 `onloadend`（**响应返回后**解析响应头，不是选文件或 FormData 问题）。
- 多见于 **Harmony** XMLHttpRequest；登录等 JSON 接口正常。

**根本原因：**

1. axios 在 XHR 完成时对 `getAllResponseHeaders()` 调用 `AxiosHeaders.from(...)`。
2. RN/Harmony 对 multipart 响应有时返回**空或 malformed 响应头**；`AxiosHeaders.from('')` 会抛上述错误。
3. **HTTP 请求可能已成功**（后台已收文件），但 JS 解析响应头失败，前端由于未捕获业务错误或异常，仍显示崩溃或上传失败。

**已确认现象（Harmony）：**

| 文件大小  | `getAllResponseHeaders()`                                                 | 结果                                                          |
| --------- | ------------------------------------------------------------------------- | ------------------------------------------------------------- |
| ~99KB JPG | 正常（`content-type: application/json`、`transfer-encoding: chunked` 等） | 上传成功                                                      |
| ~3MB PNG  | **响应头为空**                                                            | 未 patch 时 axios 抛 `header name must be a non-empty string` |

大文件响应头为空，更像是 **Harmony XMLHttpRequest + 大体积/chunked 响应** 的兼容问题，而非 PNG/JPG 格式差异。小图能过、大图 header 空，也符合这一模式。

**解决方案：**

1. 使用 patch `patches/axios+1.6.7.patch`：空/malformed 响应头 fallback 为 `new AxiosHeaders()`。
2. `npm install` 或 `npx patch-package` 自动打上。

## #009 · 鸿蒙上传大文件偶发 MalformedStreamException 及“假成功”

**日期：** 2026-05-22

**现象：**
在打上 Axios 响应头补丁（见 #008）后，虽然应用不再崩溃，但在鸿蒙上上传较大文件（如 3MB 的图片）时，有时会提示“上传完成”，但实际上后台并未收到完整文件。
查看网络请求或日志发现：

- HTTP 状态码为 `200`
- 响应内容为 `{"success": false, "code": 500, "message": "MalformedStreamException: Stream ended unexpectedly", "data": null}`

**根本原因：**

1. **底层传输 Bug**：鸿蒙 RN 原生网络模块（`XMLHttpRequest`）在传输大体积 `FormData`（如大于 2MB）时，可能发生流中断或丢包。数据还没发完连接就断开了。
2. **后端异常处理**：Java 后端正在接收 multipart 字节流，因为流突然断开，抛出了 `MalformedStreamException: Stream ended unexpectedly`。然而后端通过统一异常处理，将这个异常包在了一个 HTTP 200 的响应体中返回。
3. **前端“假成功”**：因为状态码是 200，Axios 认为请求在 HTTP 层面是成功的。如果业务代码没有显式判断 `res.success === false` 并抛出错误，就会错误地走入“上传完成”的逻辑。

**解决方案：**

由于这是鸿蒙底层网络模块的兼容性问题，目前能做的缓解措施是在前端强化**业务层错误拦截**。

1. 在上传逻辑中，拿到后端返回的数据后，必须主动检查业务状态：
   ```typescript
   const res = await dictateFeedBack(formData);
   if (!res.success) {
     throw new Error(res.message || '服务端处理失败');
   }
   ```
2. 这样前端就能正确 catch 住 `MalformedStreamException` 并提示给用户上传失败，而不是给出“假成功”的提示。
3. 若需彻底解决大文件流中断，需等待 `@react-native-oh/react-native-harmony` 网络模块的后续版本修复。

**与 #007 区分：**

| issue | 阶段     | 典型报错                               |
| ----- | -------- | -------------------------------------- |
| #007  | 发请求前 | Network Error / 网络连接失败           |
| #008  | 收响应后 | header name must be a non-empty string |

[文件上传指南](./文件上传指南.md)
