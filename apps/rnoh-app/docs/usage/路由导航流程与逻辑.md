# 路由导航流程与逻辑

## 总体架构：Flat Root Stack

项目采用 **Flat Root Stack（扁平根栈）** 架构——所有业务页面与 Main（Tabs）同级注册，避免深层嵌套（如 `RootStack → TabNavigator → SubStack → Screen` 共 4 层）。当前层级仅为 **2 层**：`RootStack → Screen`。

---

## 应用入口

`App.tsx` 按以下顺序挂载全局 Provider：

```
GestureHandlerRootView
  → SafeAreaProvider
    → Redux Provider
      → PersistGate
        → AntProvider
          ├── RootNavigator      ← 路由导航根节点
          ├── LoadingOverlay
          ├── AppUpdateManager
          └── Watermark
```

`RootNavigator`（`src/navigation/RootNavigator.tsx`）是一个薄包装，仅渲染 `RootStackNavigator`。

## 平台差异化 Stack

| 平台             | Stack 类型                             | 文件                    |
| ---------------- | -------------------------------------- | ----------------------- |
| Android / iOS    | `createNativeStackNavigator`（原生栈） | `rootStack.tsx`         |
| HarmonyOS (RNOH) | `createStackNavigator`（JS 栈）        | `rootStack.harmony.tsx` |

Metro 的 `.harmony.tsx` 扩展名解析机制在构建时自动选择正确的文件。两个文件**结构完全一致**，仅 Stack 实现和 Splash 隐藏时机略有不同：

- **Android/iOS**：`requestAnimationFrame(() => SplashScreen.hide())`
- **HarmonyOS**：`requestAnimationFrame(() => setTimeout(() => SplashScreen.hide(), 50))`（给首帧更多缓冲时间）

换闪屏图（不是改 hide 时机）见：[闪屏替换指南](./闪屏替换指南.md)。

## 登录态门控（Auth Gate）

```
RootStack.Navigator
  ├── isLoggedIn === false  →  Auth (LoginScreen)          [headerShown: false]
  └── isLoggedIn === true   →  Main (MainTabs)             [headerShown: false]
                              + ROOT_STACK_SCREEN_REGISTRY 中所有业务页面
```

- 登录状态通过 Redux 读取：`state.user.isLoggedIn`
- 用户登出时，整棵树切换为仅显示 `Auth` 页面
- 用户登录后，渲染 `Main`（底部 Tabs）及所有业务子页面

### screenOptions：谁显示顶栏、谁隐藏顶栏？

`screenOptions` 是一个函数，对**每个注册的 Screen** 都会执行一次，根据路由名返回不同的顶栏配置：

```tsx
screenOptions={({route, navigation}) => {
  if (route.name === 'Main' || route.name === 'Auth') {
    return {headerShown: false};          // ① 容器页面：隐藏 Stack 顶栏
  }
  return defaultSubStackScreenOptions({navigation});  // ② 业务页面：自定义顶栏
}}
```

**场景 1：用户已登录，看到 Main（Tabs 页面）**

```
┌──────────────────────────────┐
│   (无 Stack 顶栏 — 隐藏)     │  ← headerShown: false
├──────────────────────────────┤
│   ┌──────────────────────┐   │
│   │      HomeScreen      │   │
│   ├──────────────────────┤   │
│   │ [首页][市场][智慧][我] │   │  ← 底部 Tab 栏
│   └──────────────────────┘   │
└──────────────────────────────┘
```

`Main` 是容器页面，里面装的是整个 Tab 布局。如果显示 Stack 顶栏，会在 Tab 栏上方多出一个无用的灰色条写着「Main」。`Auth`（登录页）同理。

**场景 2：用户在 HomeTab 点击列表项，进入 `/Home/FoodCertificate`**

```
┌──────────────────────────────┐
│  ←  食品许可证到期             │  ← defaultSubStackScreenOptions 自定义顶栏
├──────────────────────────────┤   背景 #171933、白色居中标题、返回按钮
│                              │
│     (业务内容，全屏)          │  ← 无底部 Tab 栏
│                              │
└──────────────────────────────┘
```

详情页是 push 到 Root Stack 上的兄弟节点，需要带返回按钮和标题的顶栏——走 `defaultSubStackScreenOptions({navigation})`。

## MainTabs — 底部 Tab 导航

`src/navigation/mainTabs.tsx` 使用 `createBottomTabNavigator`，包含 4 个 Tab：

| Tab 名称       | 标题     | 入口组件          |
| -------------- | -------- | ----------------- |
| `HomeTab`      | 首页     | `HomeScreen`      |
| `MarketRegTab` | 市场监管 | `MarketRegScreen` |
| `SmartRegTab`  | 智慧监管 | `SmartRegScreen`  |
| `MeTab`        | 我的     | `MeScreen`        |

**Tab 本身仅为入口页**——它们不包含各自的 Stack 导航器。当 Tab 页面需要跳转到详情/业务页面时，导航目标是**根级兄弟页面**（而非嵌套 Stack 中的页面）。

底部 Tab 栏样式：

- 选中色：`#0C68F2`
- 未选中色：`#999`
- 各 Tab 使用独立的 normal/selected 图标资源

## 根级业务页面（Main 的扁平兄弟）

所有业务页面在 `src/navigation/rootStackScreenRegistry.tsx` 中按模块分组注册为扁平数组：

| 分组                     | 路由前缀      | 页面数量 | 示例路由                                        |
| ------------------------ | ------------- | -------- | ----------------------------------------------- |
| 首页（HomeTab）          | `/Home/...`   | 12 个    | `/Home/FoodCertificate`、`/Home/PendingWarn`    |
| 市场监管（MarketRegTab） | `/Market/...` | 35 个    | `/Market/DailyInspection`、`/Market/Enterprise` |
| 智慧监管（SmartRegTab）  | （暂无）      | 0 个     | —                                               |
| 我的（MeTab）            | `/Me/...`     | 2 个     | `/Me/PersonalInfo`、`/Me/DevDemo`               |

这些页面是 `Main` 的**兄弟节点**，不是 Tab 导航器的子节点。这意味着：

- 它们**覆盖整个屏幕**（底部 Tab 栏不可见）
- 共享 `defaultSubStackScreenOptions` 提供的**统一自定义顶栏**（深色背景 `#171933`、白色居中标题、自定义返回按钮）
- 从 Tab 跳转只需：`navigation.navigate('/Market/DailyInspection')`

## 懒加载机制：`lazyScreen()`

Registry 使用 `lazyScreen()` 包装器延迟 `require()` 到页面首次导航时才执行：

```tsx
function lazyScreen(getter: () => RootStackScreen): RootStackScreen {
  function LazyScreen(props: Record<string, unknown>) {
    const Cmp = getter(); // require() 仅在首次渲染时触发
    return (Cmp as Function)(props) as React.ReactElement;
  }
  return LazyScreen as unknown as RootStackScreen;
}
```

- **减少启动开销**：模块按需加载，未访问的页面不会被打包进初始 bundle
- **命名函数**：`LazyScreen` 是命名函数，避免 React Navigation 的 inline-function 警告
- **例外**：`/Market/MedicalMessage` 未使用 lazyScreen，采用直接 require

## 导航流程示意

### 典型跳转流程

```
用户打开 App
  → Redux: isLoggedIn = true
    → RootStack 渲染: Main + ~49 个业务页面
      → MainTabs 显示: [首页] [市场监管] [智慧监管] [我的]
        → 用户在 HomeTab 点击列表项
          → navigation.navigate('/Home/FoodCertificate')
            → 全屏推入（无底部 Tab 栏），自定义顶栏带返回按钮
              → 用户点击返回 → 回到 HomeTab
```

### 跨 Tab 导航

由于所有业务页面都是 RootStack 的直接子节点，跨 Tab 导航天然支持：

```
HomeTab → navigation.navigate('/Market/DailyInspection')
  → 推入市场监管的业务页面（全屏），返回首页按钮回到 HomeTab
```

## 类型系统

`src/navigation/types.ts` 定义了完整的导航类型：

- **`RootTabParamList`**：4 个 Tab 路由（均无参数）
- **`HomeRootParamList`** / **`MarketRegRootParamList`** / **`SmartRegRootParamList`** / **`MeRootParamList`**：各模块的根级业务路由及参数类型
- **`RootStackParamList`**：`Auth` + `Main` + 所有模块路由的交叉联合类型
- **`RootStackRegisteredScreenName`**：排除 `Auth`/`Main` 后所有已注册的根级页面名
- **`RootTabScreenProps<RouteName>`**：Tab 页面 Props，使用 `CompositeNavigationProp` 合并 Tab 导航和 Root 导航能力，使 Tab 页面既能切换 Tab 也能跳转根级全屏页

## 辅助模块

### `defaultSubStackScreenOptions`

为所有业务页面提供统一的顶栏配置：

- 背景色：`#171933`（`SUB_STACK_HEADER_BG`）
- 标题：白色、居中
- 返回按钮：使用 Ant Design `right` 图标旋转 180°，带 12px hitSlop
- `Auth` 和 `Main` 页面设为 `headerShown: false`

### `useSelectBridge`——通用跨页面数据回传桥接

**解决的问题：** React Navigation 的 params 必须是可序列化数据，不能传递闭包/函数。但当页面 A 跳转到页面 B 选择数据后，页面 A 需要执行回调获取选中结果——该如何处理？

我们设计并实现了一套通用的、基于路由实例 key 回溯寻址的跨页面选择桥接方案 `useSelectBridge`。

**实际场景：** 「健康证添加页」跳转到「企业选择页」过滤选择一个企业，然后把选中的企业信息回填到表单中。

```
┌──────────────────────┐          ┌──────────────────────┐
│  健康证添加页 (add)   │          │  企业列表页           │
│                      │          │  (enterprise)        │
│  1. useSelectBridge  │          │                      │
│     registerSelect(cb)│         │                      │
│                      │          │                      │
│  2. 跳转 ────────────┼────────▶│  3. 用户选中一条      │
│     不带任何Id参数     │          │     emitSelectResult │
│                      │          │     ToPrevRoute(item)│
│  4. 回调被触发 ◀──────┼──────────│                      │
│     自动回填表单      │          │  5. goBack() 返回    │
└──────────────────────┘          └──────────────────────┘
```

**调用方（add 页面）：**

```tsx
const {registerSelect} = useSelectBridge<CompanySelectItem>();

onPress={() => {
  registerSelect(company => {
    setSelectedCompany(company);
    form.setFieldsValue({
      companyName: company.companyName,
      comId: company.id,
    });
  });
  navigation.navigate('/Market/Enterprise', {selectMode: true});
}}
```

**选择页（enterprise 页面）：**

```tsx
onPress={
  selectMode
    ? () => {
        if (emitSelectResultToPrevRoute(navigation, item)) {
          navigation.goBack();
        }
      }
    : undefined
}
```

**Bridge 内部实现（`src/hooks/useSelectBridge.ts`）：**

```tsx
const callbackMap = new Map<string, SelectionCallback>();

export function registerSelectCallback(ownerId: string, cb: SelectionCallback) {
  callbackMap.set(ownerId, cb);
}

export function emitSelectResult(callbackId: string, data: any) {
  const cb = callbackMap.get(callbackId);
  if (!cb) return false;
  cb(data);
  callbackMap.delete(callbackId);
  return true;
}

export function emitSelectResultToPrevRoute(navigation: any, data: any) {
  const state = navigation.getState();
  if (!state || !state.routes) return false;
  const prevRoute = state.routes[state.routes.length - 2];
  if (!prevRoute) return false;
  return emitSelectResult(prevRoute.key, data);
}
```

#### 机制深度解析与对比

##### 三种机制对比

| 维度                  | 方案 A：本项目 useSelectBridge                            | 方案 B：Flutter / Promise 的 `await`              | 方案 C：官方推荐 `route.params`                               |
| :-------------------- | :-------------------------------------------------------- | :------------------------------------------------ | :------------------------------------------------------------ |
| **代码内聚性 (DX)**   | **极高**（回调逻辑写在触发跳转的 `onPress` 内）           | **极高**（一行代码 `const res = await navigate`） | **较低**（跳转写在 A 处，处理逻辑写在 B 处的 `useEffect` 里） |
| **路由参数污染**      | **无**（完全由 Bridge 维护，参数干净）                    | **无**                                            | **有**（参数常驻在路由中，二次进入或返回时可能重复触发逻辑）  |
| **生命周期安全性**    | **极高**（由 Hook 结合 `route.key` 管理，卸载时自动清理） | **高**（框架底层处理）                            | **极高**（完全声明式，由导航状态树管理）                      |
| **状态持久化/热重载** | **中**（内存中的闭包，App 崩溃重启或热重载后丢失）        | **中**                                            | **好**（路由参数是可序列化的 JSON，支持状态恢复）             |
| **并发/嵌套性**       | **好**（基于 `route.key` 级隔离，支持多实例、嵌套选择）   | **好**（每个 Promise 独立）                       | **好**（由页面路由栈隔离）                                    |

##### 核心设计亮点

###### 无参数污染的隐式回传

无需像传统的桥接模式那样把 `callbackId` 作为路由参数一层层地传递给下一页。通过底层在当前导航树中读取 `state.routes[length - 2]`，自动推断并定位上一个路由的 `key`（唯一实例标识）完成回调派发。这使路由参数定义更为干净，也避免了 Android/HarmonyOS 下不必要的跳转循环风险。

###### 实例级别隔离（完美解决并发与嵌套冲突）

在旧的 `companySelectBridge` 阶段，如果出现 `A -> B -> C` 的多级嵌套选择或者多窗口选择，全局唯一的单例变量会被后者覆盖，导致返回时回调丢失或错乱。
`useSelectBridge` 将缓存 Map 的键绑定为调用方页面的 **`route.key`**，这是 React Navigation 为每一个页面实例分配的独一无二的随机标识。这样，即使同一个页面在栈中被推入了多次，其各自的注册回调也会被独立保存，互不干扰，完美支持高并发与深层嵌套选择。

###### 零内存泄漏（Zero Memory Leaks）

通过在 React 自定义 Hook 中监听调用方页面的生命周期，在组件卸载（`unmount`）时自动调用 `clearSelectResultsForOwner(ownerId)`，确保缓存 Map 中的无用闭包随着页面的退出被及时垃圾回收，保证了系统内存安全。
