# Safe Area 新手说明（Android / HarmonyOS）

本文用于解释 `react-native-safe-area-context` 在 **Android** 与 **HarmonyOS（RNOH）** 上的常见表现差异，并给出两种背景布局方案（A / B）。

---

## 示例代码在做什么

```tsx
import React from 'react';
import {Text, View} from 'react-native';
import {
  SafeAreaProvider,
  SafeAreaView,
  initialWindowMetrics,
} from 'react-native-safe-area-context';

const App = () => {
  return (
    <SafeAreaProvider initialMetrics={initialWindowMetrics}>
      <SafeAreaView style={{flex: 1, backgroundColor: 'red'}}>
        <View style={{flex: 1, justifyContent: 'center', alignItems: 'center'}}>
          <Text>hello</Text>
        </View>
      </SafeAreaView>
    </SafeAreaProvider>
  );
};

export default App;
```

逐个解释：

- `**SafeAreaProvider**`：提供安全区 inset（上/下/左/右需要避开的像素值）。一般放在应用最外层（或至少导航容器外层）。
- `**initialWindowMetrics**`：提供首次渲染用的初始 inset，减少首屏“跳一下”的视觉抖动。
- `**SafeAreaView**`：会根据 inset 自动给内容留边（通常表现为 `paddingTop/paddingBottom/...`），从而让内容避开刘海、状态栏、底部手势条等区域。
- `**backgroundColor: "red"` 放在 `SafeAreaView` 上**：意味着 **SafeAreaView 自身的整块区域都会被涂成红色\*\*（它背景怎么铺，取决于平台窗口是否把状态栏区域算作 App 可绘制区域）。

---

## 为什么 Android 和 HarmonyOS 看起来不一样

这是 **平台窗口/系统栏的绘制策略差异**，不是 safe-area 用错了：

- **Android**：很多情况下“状态栏那一条区域”并不算在 RN 视图背景绘制范围内（或 Window 没设为绘制到状态栏下）。所以你会感觉“顶部被排除”，红色背景不会涂到状态栏那一条。
- **HarmonyOS（RNOH）**：更常见的是全屏绘制/背景可铺到顶层，所以 `SafeAreaView` 的背景会铺满屏幕，看起来**包括状态栏背景都是红色**。

重要的是：

- `SafeAreaView` 的核心职责是 **让内容避开 unsafe 区域**；
- “系统状态栏那条背景最终是什么颜色”属于 **窗口/系统栏策略 + 你把背景色放在哪一层**共同决定的结果。

---

## 方案 A：两端都让状态栏背景也变成红色（全红沉浸式）

### 目标

让 Android 也像 HarmonyOS 一样，状态栏那一条背景也变红（全屏视觉一致）。

### 思路

- HarmonyOS 往往天然就“背景铺到状态栏区域”；
- Android 通常需要额外设置 `StatusBar`（以及可能的沉浸式/透明状态栏配置）才能把状态栏背景控制到你想要的颜色。

示例（Android 常用）：

```tsx
import {StatusBar} from 'react-native';

<StatusBar backgroundColor="red" barStyle="light-content" />;
```

### 适用场景

- 你希望页面背景是“沉浸式大色块”，状态栏也属于页面视觉的一部分。

---

## 方案 B：两端都不把背景铺到状态栏区域（内容区红，状态栏区不染色）

### 目标

让 Android 与 HarmonyOS 都表现为：**安全区 inset 区域（例如顶部状态栏高度那条）不被红色背景填充**，只有安全区内的内容区域为红色。

### 核心做法

- `**SafeAreaView` 只负责留安全区\*\*（背景设透明或不设置）
- **背景色放到 `SafeAreaView` 里面的内容容器上**

示例：

```tsx
import React from 'react';
import {Text, View} from 'react-native';
import {
  SafeAreaProvider,
  SafeAreaView,
  initialWindowMetrics,
} from 'react-native-safe-area-context';

const App = () => {
  return (
    <SafeAreaProvider initialMetrics={initialWindowMetrics}>
      <SafeAreaView style={{flex: 1, backgroundColor: 'transparent'}}>
        <View
          style={{
            flex: 1,
            backgroundColor: 'red',
            justifyContent: 'center',
            alignItems: 'center',
          }}>
          <Text>hello</Text>
        </View>
      </SafeAreaView>
    </SafeAreaProvider>
  );
};

export default App;
```

### 适用场景

- 你希望“系统状态栏看起来像系统的”，页面背景只从安全区内容区域开始绘制。
- 你希望 Android/鸿蒙观感更统一，不被“系统栏是否参与绘制”影响。

---

## 一句话选择指南

- **想让页面背景覆盖到状态栏**：选 **方案 A**（需要特别照顾 Android 状态栏设置）
- **想让页面背景不覆盖状态栏、两端更统一**：选 **方案 B**（推荐新手默认用法）

## FAQ：为什么我用 `react-native` 自带的 `SafeAreaView` 也能工作，还要引入 `@react-native-ohos/react-native-safe-area-context`？

你在业务代码里也可能写过：

```tsx
import {SafeAreaView} from 'react-native';
```

这确实在很多场景下“能用”，但它和 `react-native-safe-area-context`（以及鸿蒙侧的 `@react-native-ohos/react-native-safe-area-context`）并不等价。

### 什么时候 `react-native` 自带 `SafeAreaView` 就够用？

- 页面很简单，只需要“内容别顶到刘海/状态栏/底部手势条”
- 不需要在任意组件里拿到 inset（上/下/左/右像素）
- 不在意不同平台/不同导航容器下的细微差异

### 引入 `react-native-safe-area-context`（跨端标准方案）能获得什么？

它提供的是一整套“可组合”的安全区体系，尤其适合导航基建：

- `**SafeAreaProvider**`：在根部计算并向下提供 inset
- `**useSafeAreaInsets()**`：在任意组件拿到 inset，做精细布局（自定义 Header、悬浮按钮、底部吸底条等）
- `**initialWindowMetrics**`：首屏更稳定，减少 inset 先 0 后更新导致的闪动
- **与 React Navigation 生态更匹配**：bottom-tabs / native-stack 等常用组合默认会依赖或推荐这套能力

### 为什么 HarmonyOS 还需要 `@react-native-ohos/react-native-safe-area-context`？

因为这是 **鸿蒙侧的适配实现**：

- **Android**：使用社区原库 `react-native-safe-area-context` 的 Android 原生实现
- **HarmonyOS（RNOH）**：需要鸿蒙适配包 `@react-native-ohos/react-native-safe-area-context`（`.har` + ArkTS 注册）才能让 Provider/insets 等能力在鸿蒙上正确工作

一句话：**简单页面可以只用 RN 自带 `SafeAreaView`，但做“导航基建 + 跨端一致性”，就应该引入 safe-area-context 的跨端方案，并在鸿蒙用对应的 ohos 适配包。**

## FAQ：为什么 `npm install` 后还要重新跑 Android/Harmony 构建？

当你安装/升级的是**带原生侧代码**的库（例如：`react-native-safe-area-context`、`react-native-screens`、`react-native-gesture-handler` 等），只重启 Metro 往往不够，原因是：

- **原生模块需要编译进 App**：Android 需要 Gradle 重新编译、重新安装 apk；HarmonyOS 需要 hvigor/DevEco 重新编译 hap。
- **“依赖树里有”不等于“已被原生链接”**：有些场景下某个库即使出现在 `node_modules`（传递依赖），也可能没有被 autolinking 稳定识别并编进二进制，导致运行时报：
  - `TurboModuleRegistry.getEnforcing(...): '<ModuleName>' could not be found`
  - `ViewManagerResolver returned null for either <ViewName> ...`

### 经验法则

- **原生库尽量作为根 `dependencies` 的直接依赖**（不要只依赖“传递依赖”）
- **安装完原生库后必做一次平台重构建**：
  - Android：重新运行 `npm run android`
  - HarmonyOS：在 DevEco 里重新 Run（必要时先 `ohpm install` 再构建）
